# 阶段 3：规格；阶段 4：分批执行

严格按 [六阶段门禁](stages.md) 执行。阶段 0～3 全部通过前禁止修改业务代码；已有局部任务也不能绕过完整迁移盘点。

沿用目标项目现有规格目录和 schema；没有时在迁移 Markdown 中组织范围、设计、规则/场景和批次。不为文档引入 OpenSpec 或猜测其 CLI 命令。已有有效规格先核对版本与缺口，不重复从头生成。

## 规格最小内容

- 范围：用户结果、入口/角色/状态、包含与排除范围、两端基线与工程限制。
- 设计：数据流、目标落点、保留/适配取舍、关键依赖与兼容影响。
- 规则/场景：条件、数据、动作、明确预期、失败与恢复、依据、验证方式。
- 全部任务：引用 [完整盘点](task-inventory.md) 的每个迁移项 ID，覆盖页面、接口、函数功能、样式及实际相关能力；写明目标文件、行为、数据、样式目标、依赖与验证方式。
- 批次：前置依赖、关联任务 ID、修改范围、关联规则/场景、复用能力、验证动作。

实现前反向检查：同一场景是否有冲突解释；展示/判断/提交值是否混淆；默认值、空值、返回、取消、重新进入是否遗漏；共享消费方及角色是否覆盖。只记录影响业务、公共结构或维护成本的关键决策，不固定每个局部变量。

## 执行规则

方案与只读模式在相应产出后结束。执行模式在阶段 0～3 门禁全部通过后进入阶段 4，继续已授权实施，不把交付方案当作迁移完成。

按可验证的业务能力及依赖拆批次，一个动作可以跨多个文件；不要把一次请求链路硬拆成无法验证的半成品。全部任务必须先在阶段 3 列出并分配批次；实施时按这些批次闭合端到端动作，不得通过优先做一个页面而延后盘点剩余内容。

每批：核对最新规格与工作区 → 实现 → 检查 diff 范围与调用方 → 执行对应门禁/场景 → 回写结果。必要公共修改单列影响和回归范围。排障期间仍遵循原范围，业务规则变化回写规格。

分别记录实现状态、代码检查、业务/视觉验证、构建与发布状态。阶段 4 新发现歧义暂停依赖批次，并回退补齐盘点、映射与规格；其他已通过前置门禁的独立批次可继续。首次阶段 3 未通过时不得提前实施任何批次。没有明确预期的场景不能标通过。

检查无关改动、意外依赖/公共配置变化、遗漏入口、临时调试、凭证、硬编码测试数据及无价值抽象。保留用户原有变更，不自动打包所有脏文件为迁移成果。
