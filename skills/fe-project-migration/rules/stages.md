# 阶段顺序与门禁

本技能严格执行阶段 0 → 1 → 2 → 3 → 4 → 5。用户要求执行迁移不等于允许跳过分析、盘点或规格。小模块可简写产物，但不能合并阶段或删除退出检查。

## 六阶段执行记录

每阶段记录：状态（未开始/进行中/通过/未通过/受阻）、输入版本、产物位置、已执行退出检查、未解决项、下一步。按阶段更新报告；未达到的阶段标未执行，不填虚假完成记录。

### 阶段 0：建立可以复核的基线

确认两端路径、分支、提交、工作区与适用规则；列出本次业务范围和相关文件初表。记录请求链路、框架/包管理器/Node/CI/容器、安装构建脚本、关键视觉状态与资料缺口。既有改动与本次修改范围分别记录。

**退出条件：** 参照版本、目标范围、工作区保护边界与缺失信息明确。资料不足时标明限制，不猜测版本；历史工时缺失不阻塞分析。

### 阶段 1：把老代码读成业务地图

只读追踪入口 → 页面 → 事件/函数 → 状态 → 最终请求 → 结果处理 → 后续页面；双向检查共享数据的生产方、消费方、持久化与清理。按 [盘点规则](task-inventory.md) 展示并落盘本次所有迁移项，含页面、路由、接口、函数功能、样式和实际存在的其他能力，附代码依据与未知项。

**退出条件：** 全部范围入口及链路已检查，迁移项类别逐一核对，清单完整，核心载荷/角色/状态可解释。业务语义未知可以带到后续分析阶段，但未读到的代码和无法确定的范围不能冒充盘点完成。

### 阶段 2：确定业务不变项与工程适配项

读取目标同类实现，对全部迁移项逐项填写保留语义、工程适配、目标位置、复用能力、影响与验证要求。保留、适配、替代、经确认删除或范围外的决定均需依据，不允许默认漏迁。

**退出条件：** 每项有合理目标落点或明确排除决定，关键请求、布局与依赖方案清楚；没有用新工程偏好覆盖业务要求。影响映射决定的未知项未解决时不得通过。

### 阶段 3：把规格写到可以执行和验收

使用项目已有规格结构，写范围、设计、规则、场景、全部任务及批次；建立迁移项 → 任务 → 规则 → 场景的关系。任务包含函数职责、参数/状态、样式目标、允许文件、依赖、实施与验证动作，不能只写页面名称。

**退出条件：** 全部在范围内迁移项已覆盖，关键歧义已解决，每项有可执行方案与明确验收预期，批次依赖和修改范围可核对。必要决定等待期间只能继续前期独立分析，禁止以“先做不受影响的页面”为由提前进入阶段 4。

### 阶段 4：批次实现与范围检查

检查阶段 0～3 门禁后，按已经列出的全部任务与批次执行。每批复核依赖、范围、规则与参考实现；实现后核对 diff、消费者、代码门禁与局部场景，分别记录实现和验证结果。布局纠偏与日志诊断属于本阶段实施工作，不构成独立快捷入口。

**退出条件：** 所有批次有明确实现终态，允许范围内的任务全部完成，无未经处理的越界改动，相关代码检查通过。实现或代码门禁受阻时不能通过；验收环境缺失可进入阶段 5 如实记录受阻，不能伪造验证结果。

### 阶段 5：验收，让规则、场景与证据能够对应

按阶段 3 场景和最终 diff 核对全范围，包括正常、边界、失败、角色、返回、历史兼容、共享消费者、视觉与容器等适用项。每项记录规则、条件、操作、预期、实际结果、状态、环境/版本与真实证据。完成报告并打开 HTML。

**退出条件：** 约定适用场景均有结果和证据记录；只在所有必需场景通过、无未解决差异时标阶段通过。失败、受阻、未执行保留对应状态，迁移不得宣称完成。不适用必须有依据。

## 回退与续接

- 新发现迁移项、规则变化或范围扩大：回到最早受影响阶段，更新完整盘点、映射、规格及批次，依次重新核对门禁后恢复。不能把新增能力直接插入实现。
- 阶段 4 新发现局部歧义：暂停依赖批次，补齐对应前期产物；其他已经通过全部前置门禁且无依赖的批次可以继续。不能借此绕过首次完整盘点。
- 阶段 5 发现实现缺陷：回到阶段 4 修复，再回阶段 5 复验；改变业务预期时回到阶段 1/2/3 更新依据，不能改测试预期掩盖错误。
- 已有方案或用户点名某批次：仍核对阶段 0～3 当前版本、全范围覆盖与退出条件。有效产物可复用，缺失阶段必须先补齐。
- 只读梳理可结束于阶段 1/2，方案结束于阶段 3；后续未执行，不属于跳跃。阶段门禁是产物与证据检查，不是要求用户每阶段重复批准。
