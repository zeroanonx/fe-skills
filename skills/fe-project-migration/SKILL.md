# 前端老项目迁移

承接已确认的业务语义与用户操作链路，使实现融入目标项目。旧代码提供现状证据，不能自动证明其中所有行为都是本次需求。

## 使用方式与范围

- `/fe-project-migration`；Codex 可用 `$fe-project-migration`，也可自然语言调用。
- **只读梳理**：用户要求熟悉、分析或盘点时，读取两端项目，交付业务地图、缺口与风险，不改业务代码。
- **迁移方案**：用户要求方案或规格时，交付映射、场景和批次，不执行迁移。
- **执行迁移**：用户要求迁移时，先完成必要梳理与规格，随后持续实现和验证；已有清晰授权无需逐阶段重复确认。

需要旧项目、目标项目位置和业务目标。沿用会话已有信息；先查仓库与资料，仍缺少时只询问影响工作的问题。目标项目不存在时，先明确创建项目的要求，不把现有项目迁移擅自扩大为搭建工程。默认前端范围，后端协议变化、旧系统停用与发布切流必须属于用户授权范围。

## 核心约束

1. 记录两端分支、提交、工作区与适用项目规则，保护既有改动；默认只写目标项目及指定交付目录。
2. 区分观察事实、已确认规则、待确认问题、改进建议。关键结论附提交、文件及函数/组件等依据。
3. 分开列业务不变项与工程适配项；权限、状态、默认值、提交参数和返回语义不能因技术栈变化而悄然改变。
4. 未明确的业务语义只阻塞依赖部分，继续独立且已明确的工作。不要用“保持旧逻辑”掩盖尚未读懂的行为。
5. 小批次按可验收的业务动作划分；实现、场景验证、构建、发布分别记录，不互相替代。

## 流程与按需加载

| 阶段 | 动作与退出条件 | 读取 |
| --- | --- | --- |
| 建立基线 | 核对版本、范围、已有改动、环境与关键参照；知道从哪里开始 | [范围与证据](rules/baseline.md) |
| 理解旧业务 | 从入口追到最终请求和后续状态，覆盖实际调用方；缺口明确 | [业务还原](rules/business-map.md) |
| 对照新工程 | 找同类实现，逐项决定保留、适配、替代或确认删除；每项有落点 | [工程映射](rules/target-mapping.md) |
| 形成规格 | 场景有条件、动作、预期与失败恢复，批次关联规则与场景 | [规格与批次](rules/specification.md) |
| 执行与复核 | 仅执行已授权模式，按依赖实现，核对 diff 与受影响消费者 | [规格与批次](rules/specification.md) |
| 验收与排障 | 选择与结论相匹配的证据，复验修复，报告失败与受阻 | [验收与诊断](rules/verification.md) |
| 交付与续接 | 汇总实际结果，生成 HTML + MD，打开并检查 HTML | [交付规则](rules/delivery.md) |

有跨页面共享状态、历史数据、角色权限、原生容器或并行入口时，额外读取 [兼容性检查](rules/compatibility.md)。简单且范围明确的模块合并文档与阶段，不机械创建所有表格；多页面、高风险迁移保留可追踪的完整链路。

## 产出

默认写入 `{目标项目}/fe-spec/project-migration/{模块}/{run-id}/`，`run-id` 使用 `YYYYMMDD-HHmmss`，冲突时追加序号；用户指定路径优先。

- `migration.md`、`migration.html`：同轮次同内容的迁移报告，包含当前模式、基线、地图、映射、规则、批次、验收结果与缺口。
- 代码、必要测试：只在执行迁移模式、已授权范围内生成。
- `evidence/`：真实截图、日志与请求记录，按需保存并脱敏；未能取得的证据写明缺口。
- `handoff.md`：仅在跨会话、未完成或需要接手时生成，记录决策、版本、有效证据、受阻项与下一步。

规格优先沿用项目已有 OpenSpec 或文档结构，不安装或强制指定工具版本。报告链接这些规格，不维护两套冲突规则。参考 [Markdown 模板](templates/migration.md) 与 [HTML 模板](templates/migration.html)，删除不适用章节，替换全部占位符。

## 与其他技能协作

可用时，编码细则使用 `fe-ai-coding`，视觉基准使用 `fe-design-analysis`，实际页面验收使用 `fe-ui-verification`。这些技能不是安装前提；缺失时按本技能细则完成工作。独立 UI 验收提出的新改进意见，先完整列出再由用户选择；用户已明确授权的迁移修复继续执行，不为调用其他技能重复询问同一授权。
