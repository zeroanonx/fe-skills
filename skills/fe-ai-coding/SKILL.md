# 前端编码分区注释与风格约束

让 AI 在写前端业务代码前先熟悉目标库风格，再重点用分区注释组织业务逻辑，并遵守团队的注释、样式和代码间距习惯。它是编码过程中的风格约束，不替代项目已有 ESLint / Prettier / Stylelint / CSSLint / TS 配置。

## 何时使用

- 用户要求编写、修改或补全前端业务代码
- 用户要求补注释、整理函数结构、统一代码分区
- 用户要求调整 CSS / Less / SCSS / Vue style，或保证样式书写顺序一致
- 触发：`/fe-ai-coding`

**不要用于**：大规模纯格式化、重构无关旧代码、给导入语句或自解释代码强行加注释。

## 优先级

1. 项目同目录已有写法
2. 项目 Lint / Formatter 配置
3. 本技能规则

若项目现有风格与本文冲突，优先沿用项目现状，并在交付时简短说明。

## 编码前置检查

写代码前必须先熟悉目标库，不要直接套模板。

- 读目标文件及同目录 2～3 个相似文件，确认命名、函数组织、注释密度、组件写法、状态管理和请求封装方式
- 读约束性配置：`package.json`、`tsconfig.json`、ESLint / Prettier 配置；涉及样式时必须检查 Stylelint / CSSLint / PostCSS 配置
- 查找可复用资产：已有组件、hooks/composables、utils、api、stores、types、常量和枚举
- 新代码放到项目既有职责目录中，不新建平行体系，不引入新的框架、状态库、请求库或样式方案，除非用户明确要求
- 如果同类代码有多个风格，以距离本次修改最近、最新、重复出现最多的写法为准

## 局部规范画像

非纯补注释的代码修改，动手前先形成本次局部规范画像。改动较大时，在对话中用 3～5 条简短说明已观察到的项目约定。

需要确认：

- 包管理器与脚本：从 lockfile 和 `package.json scripts` 判断使用 `pnpm` / `yarn` / `npm` / `bun`
- 目录职责：页面、组件、API、store、hooks/composables、types、constants 的既有边界
- 导入导出：相对路径或 alias、导入分组顺序、默认导出或命名导出、是否使用 barrel 文件
- 组件模式：props / emits / slots / v-model / hooks / store 的写法，以及同类页面的 loading / empty / error 状态
- 请求模式：是否统一走 `api` 封装、错误处理、分页字段、权限字段、响应解构方式
- 文案与配置：是否使用 i18n、字典、枚举、常量文件；有则不要在业务代码里硬编码同类内容

## CSS / 样式约束

修改 CSS / Less / SCSS / Vue `<style>` 前，先检查目标库是否配置样式校验：

```text
package.json scripts
stylelint.config.*
.stylelintrc*
.csslintrc*
csslint 配置或脚本
postcss.config.*
```

要求：

- 有 `lint:style`、`stylelint`、`csslint` 等脚本时，按项目命令校验本次样式改动；无法运行时在交付中说明原因
- 样式属性顺序以项目配置为准；无配置时参考目标文件或同目录样式文件已有顺序
- 新增选择器命名、嵌套层级、单位、颜色写法、变量使用方式必须与目标库一致
- 颜色、字号、间距、层级等优先使用项目已有变量、token、mixin 或工具类；不要随手写新的魔法值
- 只调整本次涉及范围，不为了属性排序重排整份旧样式文件
- Vue 组件样式默认保持项目现有作用域策略，如 `scoped`、CSS Modules 或全局样式入口

## 代码落地要求

- 保持最小 diff，只改完成任务必需的文件和行；不要顺手格式化无关旧代码
- 路由、权限、菜单、埋点、字典、常量、API 类型等公共契约改动需先找现有定义，不能在页面内复制一份
- 新增 UI 或交互时，复用目标库已有 loading、空状态、错误提示、确认弹窗、Toast、权限禁用等模式
- 表单、表格、分页、上传、弹窗等常见模块，优先参考同业务线已有页面的字段命名和事件命名
- 避免 `console.log`、`debugger`、废弃代码块、临时 mock 数据进入最终改动
- 不添加 `AI generated`、`由 AI 生成` 等与项目无关的标记

## 状态与异常约束

新增或修改交互流程时，必须按目标项目已有模式处理状态，不只实现 happy path。

- 异步请求至少考虑 loading、success、error、empty；提交类操作还要考虑 submitting / disabled / 防重复提交
- 错误提示使用项目已有 Toast / message / modal / error boundary 方式，不临时发明提示组件或文案格式
- 表单提交失败、上传失败、分页为空、权限不足、接口返回空数据等分支，要按同类页面已有写法处理
- watcher、定时器、订阅、事件监听、手动 Promise 等副作用要有清理或停止条件
- 不吞掉异常；确需静默失败时，注释说明业务原因，并与项目同类逻辑保持一致

## 组件边界约束

新增组件或拆分组件时，先参考目标库同类页面，不为了“看起来更现代”强行拆分或合并。

- 页面文件优先做业务编排；重复 UI、复杂表单、弹窗、表格列、上传区等可抽成项目已有风格的小组件
- 组件 props / emits / v-model / slots 的命名和类型写法，必须跟同目录或同业务线组件一致
- 子组件只接收完成职责所需的数据和事件，不把整份页面状态对象直接塞进去
- 复用已有组件优先；已有组件只缺少小能力时，优先以兼容方式扩展，不复制一个相似组件
- 不新增跨目录公共组件，除非至少有明确复用场景；否则放在当前业务模块下

## 文案与 i18n 约束

新增或修改用户可见文案时，先确认项目文案来源，不要直接硬编码一套新口径。

- 项目有 i18n、字典、文案常量、错误码映射时，必须复用或补充对应位置
- 按钮、Toast、表单校验、空状态、确认弹窗、权限提示等文案，优先参考同类页面原文
- 同一个业务状态的文案、枚举、颜色、操作按钮要同步检查，避免只改展示不改逻辑
- 不把接口返回字段名、枚举英文名直接展示给用户，除非项目已有同类约定
- 临时占位文案必须标记 TODO，并在交付中说明未确认来源

## 核心原则

- 分区注释是本技能的核心输出：新增或改造多个业务函数时，先判断逻辑归属，再放入合适分区
- 只为本次新增或修改的关键逻辑补注释，避免把旧文件改成注释墙
- 注释解释业务目的、状态含义、参数约束或非显然流程，不复述代码字面行为
- 注释语言与项目保持一致；中文业务项目默认使用中文注释
- 函数、变量、分区之间保留一个空行；不要连续堆叠多个空行
- 异步流程需要真实错误边界，不能只用注释掩盖异常处理、空状态或权限缺口
- TS 项目优先复用或补齐明确类型，不用 `any` 绕过约束

## 注释标签速查

按代码角色选择注释标签，避免同一类代码一会儿写 `@function`、一会儿写普通注释。

| 代码角色 | 标签 / 写法 | 说明 |
| -------- | ----------- | ---- |
| 业务函数 / 事件处理 | `@function` | 说明函数做什么；有参数补 `@param`，非显然返回值补 `@return` |
| Vue 业务 computed | `@computed` | 说明派生的业务含义和使用目的 |
| Hooks / Composables | `@hooks` | 说明封装能力、使用场景和关键副作用 |
| API / 请求封装 | `@api` | 说明接口用途、关键入参、返回结构和错误处理约定 |
| 导出常量 | `@constant` | 说明常量业务含义，避免魔法值 |
| 枚举 / 字典 | `@enum` | 说明枚举值含义，和后端/字典来源保持一致 |
| 局部状态变量 | `//` 单行注释 | 说明状态含义，不给自解释临时变量加注释 |

## 重点规则：分区注释

当同一文件内有多个相关函数，或逻辑自然分为查询、表单、弹窗、上传、权限等模块时，优先使用成对分区注释。导入语句不需要分区。

使用要求：

- 文件已有分区时，新增函数必须放入语义匹配的既有分区；没有合适分区再新增
- 同一文件新增 3 个及以上业务函数，或同时涉及 2 个及以上业务模块时，应先建立分区
- 分区名要表达业务职责，不写 `工具方法`、`其它`、`公共方法` 这类兜底名，除非项目旧代码已有固定叫法
- 分区内部按“状态/变量 → computed/watch → 业务函数 → 事件处理”的项目既有顺序摆放；没有既有顺序时按业务调用链摆放
- 分区注释只包业务逻辑，不包 import、类型声明、纯常量集合和简单导出

```ts
/** *********************************** S 列表查询 **************************************** */

/**
 * @function 初始化查询
 */
function initQuery() {}

/**
 * @function 获取列表数据
 */
function getTableList() {}

/** *********************************** E 列表查询 **************************************** */
```

要求：

- `S` 与 `E` 后的分区名必须一致
- 分区名使用业务动作或模块名，如 `列表查询`、`表单提交`、`文件上传`
- 小文件只有 1～2 个简单函数时，不必为了形式加分区
- 禁止只写开始不写结束，或跨越多个无关职责形成超大分区

## 函数注释

业务函数、导出函数、复杂事件处理、异步流程函数必须写 JSDoc。简单 computed、纯展示格式化函数可按项目现有习惯处理。

```ts
/**
 * @function 获取列表数据
 * @param {UserQuery} query 查询参数
 * @return {Promise<void>}
 */
async function getTableList(query) {}
```

要求：

- 必填 `@function`
- 有参数时补 `@param`
- 有非显然返回值时补 `@return`
- 函数名本身能表达的内容不要在注释里重复一遍
- `async/await` 逻辑需要错误边界，不能只补注释掩盖异常处理缺失

## Vue computed 注释

Vue 中的业务 computed 必须写 `@computed` 注释，说明它派生的业务含义和使用目的。简单透传、纯格式化且项目同类代码不写注释时，可沿用项目现状。

```ts
/**
 * @computed 已选文件数量，用于控制批量操作按钮是否可用
 */
const selectedFileCount = computed(() => selectedFileList.value.length);
```

要求：

- 必填 `@computed`
- 注释说明“是什么”和“有什么用”，不要只重复变量名
- 复杂 computed 内部应拆出语义清晰的局部变量，避免把业务判断塞进模板
- computed 只做派生状态；有副作用的逻辑应放到 watcher、事件处理或业务函数中

## Hooks / Composables 注释

自定义 hooks / composables 必须写 `@hooks` 注释，说明它封装的业务能力、使用目的和关键副作用。包括 React `useXxx`、Vue `useXxx` composable，以及项目中以 hook 命名的业务封装。

```ts
/**
 * @hooks 已选文件数量，用于控制批量操作按钮是否可用
 */
function useSelectedFileCount() {
}
```

要求：

- 必填 `@hooks`
- 注释说明 hook 封装了什么能力、给哪个业务场景使用
- 有参数时补 `@param`；返回对象字段不直观时补 `@return`
- hook 内如有请求、订阅、缓存、事件监听、定时器等副作用，必须在注释中点明
- hook 返回值命名要与项目同类 hook 保持一致，避免调用方二次猜测

## API / 枚举注释

新增或修改请求封装、接口适配、业务字典、枚举常量时，必须补充对应注释，避免调用方猜字段含义。

```ts
/**
 * @api 获取文件列表，用于列表页初始化和筛选查询
 * @param {FileListQuery} query 查询参数
 * @return {Promise<FileListResponse>}
 */
export function getFileList(query) {
}

/**
 * @enum 文件审核状态，与后端 auditStatus 字段保持一致
 */
export const FILE_AUDIT_STATUS = {
  pending: 1,
  approved: 2,
  rejected: 3,
} as const;
```

要求：

- API 注释说明接口用途和调用场景，不复制接口名
- 枚举注释说明业务来源，如后端字段、字典项、权限码或产品状态
- 新增状态值时同步检查使用方、展示文案和权限/操作矩阵
- 禁止在页面内临时复制一份同名枚举；优先复用已有 constants / enums

## 变量注释

状态变量、枚举、权限开关、表格列配置、表单默认值等需要说明业务含义；临时变量或名称清晰的局部变量不强制注释。

```ts
// 文件列表
const fileList = ref<FileItem[]>([]);

// 是否正在提交表单
const isSubmitting = ref(false);
```

导出的常量或枚举可使用 JSDoc：

```ts
/**
 * @constant 审核状态枚举
 */
export const AUDIT_STATUS = {
  pending: 1,
  approved: 2,
  rejected: 3,
} as const;
```

## 其它注释

使用标准单行注释标记后续工作：

```ts
// TODO: 接入后端返回的真实字段
// FIXME: 修复分页切换时的重复请求
```

要求：

- TODO / FIXME 必须说明具体待办，不写空泛占位
- 不保留调试注释、废弃代码块、无意义分隔线

## 校验与收尾

完成代码修改后，按项目已有脚本做最小必要校验：

- 涉及 TS：优先跑项目已有 typecheck / build / lint 脚本中的最小相关命令
- 涉及样式：优先跑 `lint:style` / `stylelint` / `csslint`
- 涉及测试覆盖区域：按项目习惯补或更新邻近测试，并跑相关测试
- 命令不可用、依赖缺失或运行超时时，在交付中说明未验证项和原因

## 交付检查

- 已观察目标文件和相似代码，新增代码风格与目标库一致
- 已确认包管理器、导入导出方式、目录职责和可复用封装
- 涉及样式时已检查 Stylelint / CSSLint / PostCSS / package scripts，并遵守属性顺序
- 涉及交互流程时，已处理 loading / empty / error / disabled / submitting 等必要状态
- 新增组件或调整组件边界时，已沿用项目 props / emits / slots / v-model 写法
- 用户可见文案已复用 i18n / 字典 / 文案常量或同类页面原文
- 新增或改造多个业务函数时，已使用或复用清晰的分区注释
- 新增或修改的关键业务函数已有必要 JSDoc
- Vue 业务 computed 已补充 `@computed` 注释，且说明派生含义和用途
- 自定义 hooks / composables 已补充 `@hooks` 注释，且说明能力、用途和关键副作用
- API / 枚举 / 导出常量已使用 `@api`、`@enum` 或 `@constant` 说明来源和用途
- 状态、枚举、权限、配置类变量有业务说明
- 分区注释成对出现，名称一致，且没有覆盖 import
- 空行清晰但不过度
- 没有为了满足格式而添加无信息量注释
- 已优先复用项目现有组件、工具函数、请求封装、类型和常量
- 已按项目脚本完成必要校验，或明确说明无法校验的原因
