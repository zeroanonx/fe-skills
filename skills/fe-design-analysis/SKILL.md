# 前端设计稿分析

把设计稿转成开发与验收可共用的视觉基准；只分析本次指定的页面和状态，不直接修改业务代码。

## 何时使用

- 用户要求分析设计稿、提取样式、梳理页面区域或 UI 还原要点
- 触发：`/fe-design-analysis`；Codex 可用 `$fe-design-analysis`，也可自然语言调用
- 需要产品流程、路由与开发任务拆解时，使用 `fe-screenshot-to-task`；需要对实际页面验收时，使用 `fe-ui-verification`

## 输入与边界

先从当前消息与项目中确定设计来源、页面/节点、状态、目标端和项目根目录。已明确的信息不重复询问；无法定位设计或缺少关键页面时询问缺失信息，其余区域可继续分析。

- 设计来源支持 Figma、Pencil `.pen`、静态截图和标注；按 [rules/tools.md](rules/tools.md) 获取证据
- 只有截图时，不编造字体、精确色值、DOM 层级、断点或交互。区分「设计标注/节点实测」「截图估算」「待确认」
- 有目标项目时，只读其适用规则、组件与 token；没有项目源码也能产出分析，不虚构代码路径
- 源设计与旧分析清单冲突时标明版本和差异，以本次明确的设计版本为准

## 产出目录

默认写入目标项目，用户指定路径时遵从用户：

```text
fe-spec/design-analysis/{页面或模块名}/{run-id}/
├── analysis.html    # 可视报告，交付时主动打开
├── analysis.md      # UI 分析清单
└── screenshot/     # 能实际保存的设计截图或局部证据
```

`run-id` 使用 `YYYYMMDD-HHmmss`，冲突加 `-2` 等后缀；不覆盖历史结果。模块名不得包含路径分隔符。没有可写目标目录时先确认落盘位置，不写入 Skill 安装目录。证据无法保存时记录可访问来源及限制，不生成虚假图片链接。

## 工作流程

1. **确定基准**：记录来源、节点/画板、版本或获取时间、设计尺寸与已提供状态；读取 [rules/analysis.md](rules/analysis.md)。
2. **建立布局图**：从上到下、从左到右、从外到里拆区域，分配稳定区域 ID；分别记录多状态与多画板。左上角为原点时，y 向下递增。
3. **逐区提取**：记录文字、图片、布局、视觉层级，补充样式、素材来源和交互状态。相同组件可引用公共规格，但保留实例差异。
4. **映射项目规范**：汇总颜色、字体、圆角、间距、阴影与透明度；查找已有 token、组件和素材；将实现建议与设计事实分开，不因个人偏好改写设计。
5. **落盘与交付**：读取 [输出检查](rules/workflow-output-checklist.md)，使用 [Markdown 模板](template/analysis.md) 与 [HTML 模板](template/analysis.html) 生成两份内容一致的报告；核对覆盖与证据后，主动打开本次 HTML。

## 交付要求

- 主动打开本次 `analysis.html` 并检查渲染，给出 HTML 与 `analysis.md` 的绝对路径链接、已分析页面/状态和主要待确认项
- 每个区域可追溯到设计节点、截图或标注；缺失信息明确标记，不填猜测值冒充实测
- 保留完整文案、图片比例/裁切、相邻关系和叠放信息；视觉分组不等同于必须采用的 DOM 结构
- 后续验收使用本次分析路径和原始设计；不将「分析完成」表述为「实现通过」

## 配合使用

| 技能 | 衔接方式 |
| --- | --- |
| `fe-screenshot-to-task` | 需要产品任务拆解时引用本清单，按该技能流程生成任务文档 |
| `fe-ai-coding` | 实现时遵循项目编码规范，引用本清单的区域与样式 |
| `fe-ui-verification` | 对照原始设计与本清单，在实际页面上验收 |

这些技能按需使用，未安装不阻塞独立的设计分析。
